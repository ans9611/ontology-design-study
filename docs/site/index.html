Ontology Design Study, 2026. A literature review, eight cases, one benchmark.

The schema sets the hops. The engine sets their price.

How you model a knowledge graph decides how much work every question needs. This study measures that: what each modelling choice costs in hops, time and memory, and which choices the graphs that lasted had in common.

What this study is about

An ontology is the shared vocabulary an organisation uses to describe its data: which kinds of things exist, and how they relate. Once applications depend on it, changing it is expensive. Yet the choices made while designing it, such as whether a relation becomes a node of its own or whether a place is a node or a text field, are rarely checked against what they will cost when the graph is queried at scale.

The study asks that question in three ways. A systematic review of the literature checks whether existing quality metrics measure cost at all (RQ1). A multiple-case study of eight industry knowledge graphs, two of them abandoned, records which design patterns each one used (RQ2). A controlled experiment models one dataset three ways and measures how the cost of twenty questions grows with the size of the graph (RQ3). Every number on this page is computed from the repository's tables when the page loads.

Terms used on this page

The study uses a small vocabulary consistently. These are the definitions it uses; they are standard in the graph-database literature [10] [20].

Ontology, knowledge graph
An ontology is an explicit specification of the kinds of things in a domain and their relations [1]. A knowledge graph is data organised under such a vocabulary, as nodes and edges [20]. This page treats the ontology as the graph's schema.
Schema
The set of node types, edge types and properties a graph uses. The experiment models one dataset under three schemas of increasing depth: flat, mid and normalized.
Hop
One step from a record to a neighbouring record along an edge, or one record visited by an index lookup or a scan. The study counts hops because they are a property of the schema, not of the engine: the same query needs the same hops on any database.
Reification (normalizing a relation)
Turning a relation into a node of its own, so that Alice knows Bob since 2014 becomes a Knows node linked to both people and carrying the date. It allows a relation to have its own properties and provenance, and it adds one hop to every query that crosses it.
Folding, denormalizing
The opposite move: storing a value such as a city name as a text property on each person instead of linking to a City node. Reading it is cheap; finding every person in a city then needs a scan or an index, and renaming the city rewrites every copy.
Scan versus index
A scan reads every record of a type to find the ones that match; its cost grows with the graph. An index jumps to the matching records; its cost grows with the answer. A reverse lookup (from a city to its people) scans unless an index or an edge exists.
Fan-in, fan-out
How many edges enter or leave a node. A city with 10,000 residents has fan-in 10,000. Uniform fan-in spreads edges evenly; heavy-tailed (Zipf) fan-in concentrates them on a few nodes, which is what real data does.
Latency exponent (slope)
The slope of log(time) against log(persons) across the six graph sizes. Near 0, the query's cost is set by its neighbourhood and does not move as the graph grows; near 1, it grows with the whole graph.

What the quality-metric literature does not measure (RQ1)

Quality-evaluation frameworks only. The benchmark literature (LUBM [25], SP²Bench [26], BSBM [27], LDBC [8]) does measure latency and scale, but holds the schema fixed and varies the engine; neither literature connects a modelling choice to its cost.

What a hop costs, per engine

A hop count is work, not cost: the same 117k-record scan is about 500× mid on the in-memory engine and 5× on Kùzu. Splitting the count into random accesses (edge traversals and index hits) and sequentially scanned records, and fitting each engine's time to the two, turns it into a cost model.

What the evidence does not show

Read these before quoting a number from this page.

One engine for the twenty questions, one dataset
The main run is an in-memory Python property graph on synthetic LDBC-SNB-shaped data. Hop counts transfer to other engines because they are the schema's; latency and memory constants do not. Six of the questions were re-run on Kùzu to show how far the constants move; no other engine was tried.
Fan-in is a construction
The main run uses uniform fan-in. The Zipf run shows what heavy-tailed fan-in does, but no real distribution was measured. Results that depend on the head of the distribution (reverse lookups, renames) will differ on real data.
Writes were measured narrowly
Four update types, one thread, no transactions, no permission checks. In an enterprise ontology with action types those often dominate.
Eight cases give associations
A purposive sample, one coder, and survivorship in what organisations publish. A pattern that co-occurs with a sustained graph is a reason to ask about it in a design review, not a cause. Grade B and C sources are evidence of practice, not of effect. "Adoption" is inferred from published accounts.
The review is screened, not yet extracted
929 candidates were screened and 188 included; the metric matrix is built from the seven frameworks. Data extraction from the full included set is the next step of the write-up.

Reproduce it

Everything on this page is generated from the repository. The main benchmark takes under an hour on a laptop; the tests take seconds.

git clone https://github.com/ans9611/ontology-design-study
cd ontology-design-study
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest                                  # schemas agree on every question

python -m ontostudy.bench               # RQ3 main run: 3 schemas × 20 queries × 6 scales
python -m ontostudy.bench --schemas flat flat_indexed mid --out docs/results/bench_indexed.csv
python -m ontostudy.bench --skew 1 --schemas flat flat_indexed mid normalized --out docs/results/bench_skew.csv
python -m ontostudy.writes              # write path
pip install -e ".[engine]" && python -m ontostudy.engine_kuzu   # second engine
python -m ontostudy.report              # regenerate the tables in docs/results/RESULTS.md
python -m ontostudy.figures             # regenerate the figures
python -m ontostudy.site                # rebuild data.json for this page

The schemas are in src/ontostudy/schemas/, the twenty questions in src/ontostudy/queries/, the pre-registered hypotheses in docs/hypotheses.md, and the review protocol in docs/protocol.md. To add a schema, implement the accessor interface in schemas/base.py; the queries and the harness need no change.
